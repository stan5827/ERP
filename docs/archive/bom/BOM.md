BOM（Bill of Materials）是製造業的「數據核心」，它本身雖然是一個基礎主檔（Master Data），但它的存在會直接決定以下四大類表單的產生與內容：
1. 工程研發與變更維度

當原始 BOM 需要修正時，會產生「變更類」表單，確保生產現場不會用錯版本。

    ECN (Engineering Change Notice) 工程變更通知單：當 BOM 的組成零件替換時，必須產生此單據來驅動舊料耗盡或立即切換。

    ECR (Engineering Change Request) 工程變更申請單：在正式修改 BOM 前，由研發或品管發起的評估表單。

2. 生產執行維度（核心關聯）

這是 BOM 最頻繁被調用的地方，沒有 BOM，下列表單將無法運算用量。

    生產工單 (Work Order)：工單會「繼承」BOM 的內容。

    領料單 (Material Requisition)：系統根據工單上的 BOM 明細，自動產生該去倉庫領取的物料清單。

    退料單 (Material Return)：若生產剩餘或發生不良，參考 BOM 原本定義的組件進行退庫。

    補料單 (Material Supplement)：若生產過程中發生損耗，超出 BOM 標準用量的部分需以此單據記錄，用以核算「超耗」。
	
3. 物料需求計劃 (MRP) 與採購維度

BOM 是計算「買什麼、買多少」的乘數。

    MRP 運算結果表 (MRP Suggestion)：系統將「訂單需求」乘上「BOM 階層」，產生建議的採購清單。

    採購請購單 (Purchase Requisition)：當 MRP 發現庫存不足以支應 BOM 需求時，自動生成的內部申請單據。

    委外加工單 (Subcontract Order)：若 BOM 中定義某個半成品是委外製作，則會產生此單，並附帶「撥料清單」（供料給加工商）。

4. 成本與財務維度

    標準成本捲算表 (Cost Roll-up)：財務系統會抓取 BOM 的物料組成，加上人工與製費，計算出產品的「標準成本」。

    差異分析報表：對比「BOM 標準用量」與「領料單實際耗用」的差異。
	
階段,產生/關聯表單,主要作用
設計期,ECN / ECR,控制 BOM 版本的準確性與有效日期
計劃期,MRP 建議單 / 請購單,根據 BOM 計算原材料的採購缺口
執行期,領料單 / 欠料清單,依 BOM 定義的比例從倉庫撥付物料
委外期,委外撥料單,提供給外協廠加工所需的組件清單
結算期,成本差異分析表,比較實耗與 BOM 標準的成本落差

既然我們已經釐清了 BOM（物料清單） 與 生產工單 之間的表單流轉邏輯，接下來在開發或架構 ERP 系統時，有幾個關鍵的**「數據連動節點」**是你需要特別注意的：
關鍵數據連動節點

    自動扣料（Backflush）邏輯：
    當工單完工入庫時，系統是否要根據 BOM 標準用量 自動扣除倉庫庫存？這能節省手動過帳時間，但前提是您的 BOM 必須非常準確。

    多階 BOM 的拆解：
    如果一個產品有半成品（Sub-assembly），建立工單時是要「一階一階開工單」，還是由系統自動觸發「子工單」？這會影響到生產排程的複雜度。

    替代料（Substitute Material）處理：
    當 BOM 裡的 A 料缺貨時，工單是否允許領取 B 料？這需要在領料單與工單用料明細中建立「替代關係」的紀錄。
	
輔助建立 BOM 的功能設計，重點在於**「減少重疊輸入」與「確保數據一致性」**。以下是專業 ERP 系統中常見的高級輔助功能：
1. 快速建立工具（Efficiency Tools）

    BOM 複製功能 (Save As / Copy From)：

        邏輯：允許使用者選取現有的相似產品 BOM，一鍵複製成新產品的草稿，僅需修改差異部分。

        進階版：支援「批次替換某個共用零件」，例如將 A 系列產品的所有螺絲從規格甲改為規格乙。

    CAD/EDA 集成插件 (CAD Integration)：

        邏輯：直接從 SolidWorks、AutoCAD 等設計軟體匯出物料表（Drawing BOM），透過 API 直接轉入 ERP 的工程 BOM (EBOM)。

        效果：消除研發與製造之間的排版謄寫錯誤。

    Excel 批次導入與校驗：

        功能：提供標準 Template，支援「先校驗、後匯入」。系統在匯入前自動檢查「料號是否存在」、「單位是否匹配」。

2. 智慧防錯機制（Validation Logic）

    遞迴循環檢查 (Recursion Check)：

        邏輯：系統自動檢查 BOM 結構中，是否有「母件同時身為自己的子件」的邏輯衝突。

    低階碼自動運算 (Low Level Code Calculation)：

        技術點：在儲存 BOM 時，系統自動計算該物料在所有結構中的最低層級。這是未來執行 MRP 展開時，保證運算順序正確的關鍵。

    工程生命週期檢核：

        功能：若子件料號處於「停用」、「作廢」或「設計中」狀態，系統應禁止該 BOM 發佈至生產端。

3. 版本與異動管理（Version Control）

    BOM 差異比對 (BOM Comparison)：

        介面設計：提供「左右對照表」，以紅、綠色標示出兩個版本（或兩個相似產品）之間，哪些物料有增減或用量變動。

    批次工程變更 (Mass ECN)：

        情景：當某個共用零件停產時，系統能列出所有使用該零件的 BOM，並讓使用者一次性勾選，批次完成「舊換新」的 ECN 流程。

技術架構建議：資料表設計重點

在建立輔助功能時，您的資料庫設計（Table Schema）應考慮以下欄位：

    虛擬件標記 (Phantom Item)：該組件是否僅為邏輯組合，生產時直接展開至下一層。

    損耗率 (Scrap Factor)：定義該零件在生產過程中的標準損耗（如：10%），工單展開時會自動增加預計領料量。

    生效/失效日期 (Effective/Expiry Date)：控制 BOM 行項的時效性，實現「定時切換」零件的功能。

    右側詳情面板：點選特定行時，顯示該物料的庫存狀況或規格參數。

    顏色編碼：

        <span style="color: #d32f2f;">紅色 (Red)</span>：B 版本已刪除（A 版本存在）的物料。

二、 「低階碼 (Low Level Code)」SQL 運算邏輯

低階碼 (LLC) 是指一個物料在所有 BOM 結構中所處的最底層級。根節點（成品）為 0，其子件為 1，以此類推。如果同一個零件出現在不同的層級，則取其最大值（最底層）。

這在執行 MRP 時至關重要，系統必須從 LLC 0 開始算到 LLC N，確保上層需求彙總後才計算下層。
SQL 實作範例 (使用遞迴 CTE)

假設您的 BOM 表結構如下：

    Parent_Item (母件)

    Child_Item (子件)
	
	-- 使用遞迴公用表運算式 (Recursive CTE) 計算層級
WITH BOM_Hierarchy AS (
    -- 1. 定義根節點 (成品)：假設成品沒有人把它當子件
    SELECT 
        Child_Item, 
        0 AS Level
    FROM BOM_Table
    WHERE Parent_Item NOT IN (SELECT Child_Item FROM BOM_Table)
    
    UNION ALL
    
    -- 2. 遞迴展開子件
    SELECT 
        b.Child_Item, 
        bh.Level + 1
    FROM BOM_Table b
    INNER JOIN BOM_Hierarchy bh ON b.Parent_Item = bh.Child_Item
)
-- 3. 取得每個物料的「最大層級」作為低階碼
SELECT 
    Child_Item AS Item_No, 
    MAX(Level) AS Low_Level_Code
FROM BOM_Hierarchy
GROUP BY Child_Item
ORDER BY Low_Level_Code ASC;

邏輯說明：

    遞迴尋找：從沒有母件的頂層成品開始，逐層往下找。

    層級累加：每下一層，Level 加 1。

    取最大值 (MAX)：這是關鍵！如果螺絲 A 同時出現在第一層和第三層，它的 LLC 必須是 3。

    性能優化：在實際 ERP 環境中，這個運算通常在 BOM 儲存時觸發一次，並將結果回填至「物料主檔」的 Low_Level_Code 欄位中。
	
以下我為您準備了 「BOM 扁平化資料表（Closure Table）」 的設計方案，以及針對 「替代料」 的前端互動建議。
一、 數據結構：BOM 閉包表 (Closure Table) 設計

傳統的 BOM 表（Parent-Child）在查詢「某零件被哪些成品用到（Where-used）」時非常吃力。閉包表透過空間換取時間，記錄所有祖先與後代的關係。
1. 資料表結構 (Schema)

表名：BOM_Path
| 欄位名 | 型態 | 說明 |
| :--- | :--- | :--- |
| Ancestor | String | 祖先物料編號 (可能是母件、祖母件或頂層成品) |
| Descendant | String | 後代物料編號 (子件、孫件等) |
| Distance | Int | 距離 (0: 自己, 1: 直接子件, 2: 孫件...) |
| Path_ID | String | 路徑識別碼 (用來區分同一個零件在同個 BOM 裡的不同位置) |
2. 查詢優勢

    找某成品下的所有零件：SELECT Descendant FROM BOM_Path WHERE Ancestor = '成品A'

    找某零件被哪些成品使用：SELECT Ancestor FROM BOM_Path WHERE Descendant = '螺絲B' AND Distance > 0

1. 工單用料明細中的「展開模式」

        替換比例 (有些替代料可能是 1 換 2)

在展開 BOM 時，您會遇到一種特殊的物料叫 「虛擬件」。它在系統中不領料、不入庫，僅為了歸類。

二、 工單改製（工單中途修改 BOM）異常處理流程

「工單改製」是 ERP 最頭痛的場景，因為它涉及「已發生的實體物料動向」與「未發生的系統預算」之間的衝突。
1. 改製場景分類

    情境 A (尚未領料)：最單純，直接修改工單用料明細（Pick List）並重新計算預約庫存。

    情境 B (已領料，未生產)：需要處理「多餘料件」的退庫與「新缺料」的補領。

    情境 C (已報工，半成品已產出)：最複雜，涉及工序調整與半成品拆解。

2. 標準處理流程設計

當按下「工單改製」時，系統應啟動以下自動化邏輯：

    鎖定工單 (Soft Lock)：防止在改製運算期間，現場人員繼續進行領料或報工。

    差異分析 (Gap Analysis)：

        比對「原始工單 BOM」與「改製後 BOM」。

        產生 差異清單：標註哪些料要「退回倉庫」、哪些料要「補發」。

    生成變更單據：

        自動產生 紅字領料單 (退料)：對應已被領出但新 BOM 不需要的部分。

        自動產生 超耗/補領單：對應新增加的零件需求。

    重新計算成本中心：

        將改製產生的損失（如報廢、拆解工時）記錄到特定的「改製損失費」科目，而非產品標準成本。

3. 異常防呆機制

    領料不准改：若零件已投入無法拆解的製程，系統應禁止改製，強制要求「工單報廢」並重新開立。

    庫存連動檢查：若改製後的零件庫存不足，系統應跳出「MRP 警告」，告知改製將導致停工待料。
	
一、 利用 Redis 優化 BOM 查詢效能

當系統規模擴大時，頻繁的遞迴查詢會成為資料庫（DB）的負擔。
1. 緩存策略：Hash 結構儲存

不要只把 JSON 字串存入 Redis，建議使用 Redis Hash 儲存「已展開的片段」。

    Key 設計：BOM:TREE:{Product_No}:{Version}

    效能提升：

        讀取：前端請求時，先查 Redis。命中則直接回傳（速度 <10ms）。

        更新：當發生工程變更（ECN）時，主動刪除（Purge）該成品及受影響上層成品的快取。

2. 預熱機制 (Cache Warming)

在每天淩晨或 MRP 執行前，系統自動將「常用成品」的 BOM 樹預先算好並塞入 Redis，確保白天高頻作業時的極致體驗。

當生管人員點擊「改製」時，系統應跳出對照視窗，幫助他們判斷「物料要怎麼動」。
1. UI 佈局 (Layout)

    左側：原始用料明細（呈現當前已領、未領狀態）。

    右側：新版用料預算（呈現改製後的理論需求）。

    下方：動作清單 (Action List)：這是核心，系統自動計算出的「處置建議」。

在後端執行改製存檔時，必須包在一個 Transaction (事務) 內，確保數據一致性：

    UPDATE Production_Order_Header：更新版本號與改製原因。

工單改製：報廢與損失處理流程

在改製過程中，最常見的損失來自於：已加工的半成品無法拆解，或是拆解過程中造成零件損壞。
1. 損失分類與判定

系統應提供一個介面，讓現場品管（IPQC）或生管針對差異物料進行「處置判定」：

    可重用 (Rework/Reuse)：退回倉庫，不產生損失。

    報廢 (Scrap)：無法再使用，必須計入工單成本。

    轉用 (Divert)：轉給其他工單使用（需執行移轉單）。

2. 過帳邏輯：損失歸屬

在財務帳務上，改製產生的損失通常不建議直接混入「標準物料成本」，否則會誤導毛利分析。

    獨立科目：建議系統自動將報廢金額轉入「生產損失－工單改製」會計科目。

    成本核算公式：
    工單總成本=(實際領料−實際退料)+報廢物料成本+已發生加工費

三、 「工單改製損失」管理介面設計

生管人員需要一個清晰的清單來確認哪些東西要丟掉，哪些要留著。
UI 功能要點：

    處置勾選框：每一筆差異料件後方都有 [退庫 / 報廢 / 轉用] 的選項。

    損失試算：當使用者勾選「報廢」時，系統即時顯示該筆報廢對應的 金額損失。

    原因代碼 (Reason Code)：強制要求輸入改製原因（如：客戶需求變更、設計錯誤、資材缺料），以便後續進行大數據分析，找出改製頻率最高的根因。

四、 系統自動化動作 (Automation)

當改製審核通過後，系統應執行以下連動：

    自動產出「報廢單」：針對判定為報廢的物料，扣減該工單的在製品（WIP）價值。

    自動產出「拆解入庫單」：針對可重用的部分，將其從工單退回倉庫。

    更新工單狀態：將工單標記為「已改製」，並在歷程紀錄（Audit Trail）中保留改製前的 BOM 快照，以供日後審計。
