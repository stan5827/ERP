# ERP 專案修復規劃文件

- 分析日期: 2026-05-03
- 分析範圍: 前端 (`erp-frontend`)、API/Gateway (`ErpGateway`)、後端 (`ErpBackend`)、資料庫/遷移、端到端流程
- 驗證方式: 原始碼盤點、設定檔檢查、`npm run build`、`dotnet build ERP.sln`、`dotnet test ERP.sln --no-build`

## 1. 執行摘要

目前 ERP 倉庫已具備「大型單體 ERP + 前端 SPA + API Gateway + PostgreSQL + 測試專案」的基本骨架，但系統實際狀態屬於「後端可編譯、前端不可發版、跨層契約失真、流程未真正打通」。

最重要的結論如下:

1. 前端正式建置失敗，代表目前無法穩定交付或部署。
2. API 契約已與畫面、hooks、模組拆分脫節，屬於結構性問題，不是單一 typo。
3. 後端雖可建置且 61 個測試通過，但至少 33 個 Controller 仍是 placeholder，許多模組尚未真正可用。
4. 資料庫模型極大，但 migration 只有單一主遷移，且啟動時混入大量 seed/init，存在 schema drift 與環境不一致風險。
5. 採購、收貨、供應商 ASN、系統監控、預算分析等流程存在明顯斷鏈。
6. 安全面有多個高風險項: 預設密碼展示、硬編碼管理重設 secret、硬編碼資料庫帳密、Gateway fallback JWT key。

結論: 這個專案不適合直接以「補單點 bug」方式修復，應改用「先恢復可建置、再恢復核心流程、再清理架構債」的分階段修復策略。

## 3. 分層診斷

## 3.1 前端

### 主要問題

1. API 契約漂移
   - `src/api/procurementApi.ts` 依賴 `GoodsReceiptDto`、`SupplierAsnDto`，但 `src/api/api.ts` 未提供對應匯出。
   - `SystemMonitoring.tsx` 依賴 `systemMetricsApi`，`TaskMonitor.tsx` 依賴 `systemJobsApi`，但 API 聚合層不存在這些匯出。
   - `BudgetAnalysis.tsx` 依賴 `useBudgetAnomalies`、`useBudgetAlerts`、`useBudgetAnalysis`，但 `useApi.ts` 未提供。

2. UI 元件體系半導入
   - `src/components/ui/*.tsx` 引入 `@/lib/utils`，但 `tsconfig.app.json` 未設定 `paths` / `baseUrl`。
   - 這些元件又依賴 `@radix-ui/react-slot`、`class-variance-authority`、`clsx`、`tailwind-merge`，但 `package.json` 未宣告。
   - `zod` 被多個 schema 檔使用，但 `package.json` 亦未宣告。

3. Context/hook 介面不一致
   - `useApiErrorHandler.ts` 呼叫 `useToast().showError`，但 `useToast.tsx` 僅提供 `addToast/removeToast/clearAll`。

4. 組件 API 漂移
   - `MrpPlanning.tsx`、`ProcurementModals.tsx` 傳入 `isOpen`、`schema` 等 props，但目前 `FormModalProps` 介面不接受。

5. 維護狀態失控
   - `src/pages` 目錄混入大量一次性修補腳本，表示多人/多輪修復未回收，技術債已直接滲入正式前端程式區。

### 影響

- 前端目前不具備可持續交付能力。
- 功能是否能用，不能只靠頁面存在判斷，很多頁面可能連 build 都過不了。
- 後續每新增一個功能，都會再擴大 API/type/props 漂移。

## 3.2 API / Gateway

### 主要問題

1. 前端未統一走 Gateway
   - 前端 `src/api/api.ts` 直接指向 `http://localhost:5100/api/erp`
   - Gateway `appsettings.json` 已配置 `/api/erp/*` 代理，但實際前端未真正以 Gateway 為單一入口

2. 安全設定不一致
   - `ErpGateway/Program.cs` 對 JWT key 設有 fallback 明碼
   - Backend 則要求 `JWT_SECRET_KEY` 至少 32 字元
   - 兩端策略不一致，部署時容易出現驗證成功/失敗不一致

3. CORS 與入口位址硬編碼
   - Backend、Gateway 都把 localhost ports 寫死在程式中
   - 不利於 staging / production / container 環境切換

### 影響

- 入口治理失敗，難以做統一認證、流量控制、監控與版本管理。
- 環境切換成本高，容易出現「本機可跑、整合環境失敗」。

## 3.3 後端

### 主要問題

1. Controller 完成度落差極大
   - 約 90 個 Controller 中，至少 33 個仍是 placeholder。
   - 例如 `GoodsReceiptsController` 只回傳修復中訊息，但前端採購/ASN/收貨流程已依賴它。

2. 啟動程式承載過多責任
   - `Program.cs` 同時處理:
     - DI 註冊
     - JWT/CORS
     - 健康檢查
     - DB 啟動邏輯
     - 大量 seed 資料
     - admin 初始化
   - 導致啟動流程過重，責任邊界不清楚，也增加測試與部署風險。

3. 安全風險
   - `AuthController` 存在硬編碼 `ERP_ADMIN_RESET_2026`
   - `seed-admin/Program.cs` 使用硬編碼 PostgreSQL 帳密與 `admin123`
   - 首頁登入頁直接展示預設帳號密碼

4. 實作品質不一致
   - 後端 build 雖通過，但仍有 async 無 await、nullable warning 等訊號。
   - 測試數量並不能覆蓋 placeholder controller 與跨流程問題。

### 影響

- 後端目前比較像「部分模組可用、整體平台未完工」。
- 若直接開放使用，業務流程會在某些節點直接中斷。

## 3.4 資料庫與遷移

### 主要問題

1. `ErpGeneralDbContext` 極大
   - 涵蓋 HR、Inventory、MES、Sales、Procurement、RD、Asset、Finance、Portal、Collaboration 等大量 bounded contexts
   - 單一 DbContext 與單體 migration 使 schema 變更成本與風險同步放大

2. migration 策略偏弱
   - 目前可見 migration 幾乎只有單一主遷移與 snapshot
   - 與龐大的模型規模不成比例

3. 啟動時 seed 過多
   - 啟動時直接建立類別、會議室、假日、admin、倉庫、SKU、MES 基礎資料
   - 容易導致:
     - 環境資料漂移
     - 測試資料與正式資料混雜
     - 重跑環境時的不可預期行為

4. 遷移工具缺失
   - `MigrationApp` 缺乏可維護原始碼，無法作為正式資料庫修復鏈的一部分

### 影響

- Schema 管理與資料初始化尚未產品化。
- 一旦多環境並行，DB 一致性會成為主要風險來源。

## 3.5 流程層

### 已辨識的高風險斷鏈

1. Procure-to-Pay
   - 前端已有採購單、ASN、收貨相關 API 呼叫
   - 後端 `GoodsReceiptsController` 仍是 placeholder
   - 代表請購/採購/到貨/驗收/入庫/AP 流程未真正打通

2. Supplier Portal / ASN
   - 前端存在 `supplierAsnsApi` 與供應商入口頁
   - 後端 `SupplierAsnController` 仍為 placeholder

3. Budget Analysis
   - 前端分析頁依賴 hooks 不存在
   - 屬於畫面先行、資料流程未落地

4. Monitoring / Background Jobs
   - 前端系統監控與任務監控頁存在
   - 但 API 匯出缺失，後端對應能力也未完整聚合

5. Login / Bootstrap
   - 測試與畫面預設使用 `admin/admin123`
   - 但後端啟動邏輯又可能隨環境變數生成隨機密碼
   - 實際環境行為不一致

## 4. 修復優先級

### P0: 立即處理

1. 拔除硬編碼憑證與 secret
   - `seed-admin` 資料庫帳密
   - `admin123`
   - `ERP_ADMIN_RESET_2026`
   - Gateway fallback JWT key

2. 恢復前端可建置
   - 先讓 `npm run build` 通過
   - 包含 API 匯出整理、缺失依賴補齊、alias 修正、壞掉 hooks/props 修復

3. 關閉或隱藏未完成模組入口
   - 對 placeholder controller 對應的前端頁面與選單加上 feature flag 或暫時下架

### P1: 核心流程恢復

1. 打通登入與權限流程
2. 打通採購到收貨主流程
3. 打通庫存主資料與基本異動流程
4. 打通工作單 / MRP 的最小可行流程

### P2: 架構整治

1. 前端 API client 模組化與型別單一真源
2. 後端 seed / init / migration 分離
3. 建立 Gateway 為唯一 API 入口
4. 建立端到端 smoke test

### P3: 長期優化

1. 分域測試覆蓋率提升
2. 資料庫 migration 治理
3. 可觀測性與背景任務治理
4. 模組分層與 bounded context 清理

## 5. 建議修復路線圖

## Phase 1: 7 天內恢復「可發版骨架」

目標:

- 前端 build 成功
- Backend/Gateway 啟動策略一致
- 所有硬編碼憑證移除
- 未完成模組不再對外暴露

工作包:

1. 前端依賴與 tsconfig 整理
2. API 聚合層盤點與重新匯出
3. 清理/隔離 `src/pages` 內修補腳本
4. 加入 feature flags
5. 安全設定改成 env/config 注入

驗收:

- `npm run build` 成功
- `dotnet build ERP.sln` 成功
- 登入頁不再顯示固定密碼

## Phase 2: 2 到 3 週恢復「核心營運流程」

目標:

- 最少恢復以下主流程:
  - Login / User / Role
  - Purchase Requisition -> PO -> ASN -> Goods Receipt
  - SKU / Warehouse / Inventory Transaction
  - MRP 最小可行流程

工作包:

1. 逐一比對前端頁面、hook、API client、controller、DTO
2. 對 placeholder controller 列出保留/刪除/補實作清單
3. 補齊缺失 DTO 與 API 契約測試
4. 為核心流程建立 e2e smoke tests

驗收:

- 至少 4 條主流程在測試環境可完整操作
- Playwright smoke tests 可執行且不依賴手動修資料

## Phase 3: 3 到 6 週完成「結構穩定化」

目標:

- 建立可持續維護的全端協作模式

工作包:

1. 建立 OpenAPI 或共享型別產生流程
2. 以 domain 拆分前端 API modules 與 hooks
3. 將 seed logic 從 `Program.cs` 拆至 migration/initializer pipeline
4. 建立 migration 管理規範
5. 為每個核心 domain 增加 service/unit/integration tests

驗收:

- 新增模組不再靠手寫重複 DTO 與散落 hooks
- DB migration 與 seed 可在 CI/staging 重複執行

建議依以下順序開工:

3. Placeholder controller 與前端選單對照表
4. 採購到收貨流程打通
5. 監控/背景任務 API 補齊
6. DB migration 與 seed 重整

## 8. 判斷標準

當以下條件同時成立，才算修復進入穩定狀態:

1. 前端與後端都可在乾淨環境建置
2. 所有核心入口都不依賴硬編碼帳密
3. 前端頁面不再引用不存在的 API/hook/type
4. Placeholder controller 已移除、補實作，或從 UI 下架
5. 至少 4 條核心 ERP 流程具備自動化 smoke test
6. migration 與 seed 可以在新環境可重複落地

## 9. 總結

這個 ERP 倉庫目前最大的問題不是「某個功能壞掉」，而是:

- 前端、API、後端、資料庫之間沒有共享且受控的契約
- 修補行為長期直接寫入正式程式區
- 未完成模組仍暴露到 UI 與 API 層
- 安全與初始化策略尚未產品化

因此修復策略必須從「流程恢復 + 契約收斂 + 環境治理」三條線並行推進，才能把這個專案從可演示狀態拉回可交付、可維護、可上線的狀態。
