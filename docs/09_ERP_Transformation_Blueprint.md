# ERP 改造藍圖文件

版本: v1.0  
日期: 2026-04-26  
專案目錄: `D:\ERP`

## 1. 文件目的

本文件定義本 ERP 系統未來 12 到 18 個月的正式改造藍圖，作為管理決策、需求排程、架構重整、流程治理、教育訓練與驗收評估的共同依據。

本藍圖的核心目標是將現有系統從「模組齊備但流程閉環不完整的 ERP 雛形」，提升為：

- 以單一數據源為核心的流程平台
- 可配置、可整合、可擴展的模組化系統
- 以使用者採用為前提的企業營運工具
- 能支援管理決策與預測分析的經營平台

## 2. 改造願景

### 2.1 願景聲明

建立一套以主資料治理、跨模組流程整合、配置驅動架構與決策分析能力為核心的 ERP 平台，支援公司營運、管理、協作與持續成長。

### 2.2 業務價值主張

- 打破資訊孤島，讓業務、採購、生產、庫存、財務看到同一份真實資料
- 以自動化減少重工與人工作業風險
- 讓流程能隨組織變化而調整，而不是每次調整都要改核心程式
- 讓系統從資料記錄工具升級為管理決策平台

## 3. 目前現況摘要

### 3.1 已具備基礎

- 前後端分離架構已建立
- 多數 ERP 模組頁面與後端 API 已存在
- 資料庫模型完整度高，涵蓋 HR、Inventory、MES、Sales、Procurement、Finance、Budget、ESG 等模組
- 測試基礎已存在，後端單元測試與整合測試可執行

### 3.2 目前主要問題

1. 前端 API 契約與後端 DTO 偶有漂移
2. 部分模組已有 UI，但交易閉環未完整
3. 前端 `api.ts` 與後端 `DbContext` 集中度高，擴充與維護成本偏高
4. 全域 payload 攔截與轉換規則過重，易產生隱性錯誤
5. 報表與分析頁面已存在，但分析資料層尚未標準化
6. 部分流程未真正落地，例如 `SupplierAsn`

### 3.3 已驗證的技術狀態

截至 2026-04-26：

- 後端可建置
- 前端可建置
- 後端測試可通過
- 系統具備持續改造基礎

## 4. 改造原則

### 4.1 業務優先

所有技術重整都必須服務業務流程閉環，而不是只追求程式結構漂亮。

### 4.2 單一數據源

主資料與關鍵交易資料必須有唯一可信來源，不允許不同模組各自維護同義資料。

### 4.3 配置優先於硬編碼

流程、審批、欄位規則、通知與整合設定，優先設計為可配置，而非散落在頁面與 controller 中。

### 4.4 分階段落地

先穩定，再整合，再智能化，避免在資料不一致與流程未閉環前過早堆疊 AI 與 BI。

### 4.5 使用者採用導向

ERP 的成功標準不是功能數量，而是跨部門是否持續使用，資料是否可信，流程是否真正落地。

## 5. 改造目標

### 5.1 流程整合與數據一致性

目標：

- 建立主資料治理
- 建立跨模組交易追溯鏈

- 關鍵單據不需跨模組重複輸入相同資訊

## 6. 目標架構藍圖

### 6.1 應用架構

建議架構分為五層：

1. 表現層  
   `erp-frontend`  
   負責 UI、互動、表單、圖表、角色化操作體驗

2. 應用服務層  
   `ErpBackend/Controllers + Services`  
   負責用例協調、流程控制、狀態轉換、整合服務

3. 領域規則層  
   逐步整理於 `Services`、`Validation`、後續可拆的 domain 模組  
   負責業務規則、驗證、編號、單據邏輯、狀態機

4. 資料存取層  
   `ErpGeneralDbContext`、Entity Configurations、Repository / Query Service  
   負責資料一致性、查詢、交易與 migration

5. 整合層  
   未來新增 `Integrations` 或 `Connectors`  
   負責 CRM、電商、供應商平台、外部財務或物流系統對接

### 6.2 數據架構

數據分為三類：

- 主資料  
  SKU、UOM、客戶、供應商、倉庫、儲位、部門、成本中心、員工、工站

- 交易資料  
  SO、PO、PR、ASN、GR、WO、領料、完工、出貨、發票、應收應付、預算執行

- 分析資料  
  KPI、預警、成本分析、庫存分析、產能分析、預算分析、ESG 指標

目標狀態：

- 主資料有單一來源
- 交易資料有上下游關聯
- 分析資料自交易資料與主資料穩定產生

### 6.3 配置架構

建立下列可配置能力：

- 審批流程配置
- 狀態轉換規則配置
- 欄位顯示 / 必填 / 預設值配置
- 單據編號規則配置
- 通知規則配置
- 外部接口端點與授權配置

## 7. 核心改造方案

### 7.1 主資料治理

優先治理主資料：

- SKU
- UOM 與換算
- Supplier
- Customer
- Warehouse / Bin
- Department / CostCenter
- WorkCenter / Routing / BOM

具體修改：

1. 為每種主資料定義唯一鍵與停用規則
2. 後端集中主資料驗證與重複檢查
3. 前端所有選單改由主資料 API 供應
4. 補齊主資料異動審計與版本追蹤

### 7.2 流程狀態機

優先流程：

- `PR -> RFQ -> PO -> ASN -> GR -> AP`
- `SO -> Demand -> WO -> Issue -> Completion -> Shipment -> AR`
- `Budget Plan -> Execution -> Alert -> Analysis`

具體修改：

1. 為各交易建立狀態機
2. 只允許透過 service 執行狀態變更
3. 寫入交易歷程與關聯資料
4. 為關鍵狀態切換建立事件與通知

### 7.3 表單與契約標準化

具體修改：

1. 拆分 [api.ts](/D:/ERP/erp-frontend/src/api/api.ts) 為模組 API
2. 建立共用表單 schema
3. hook 一律回傳解包後資料
4. 降低全域 interceptor 的隱式處理範圍
5. 高頻單據統一欄位命名與 DTO 定義

優先單據：

- SKU
- Purchase Order
- Sales Order
- Work Order
- Goods Receipt
- Employee

### 7.4 外部整合能力

整合對象：

- 電商訂單平台
- CRM
- 供應商平台
- 物流 / 運輸系統
- 銀行 / 外部財務系統

具體修改：

1. 設計標準 REST API
2. 補 webhook 機制
3. 建立 integration service 與錯誤重送機制
4. 整合資料與核心交易資料分層

### 7.5 BI 與預測能力

具體修改：

1. 建立分析查詢服務層
2. 定義標準 KPI 字典
3. 建立主題式 dashboard
4. 先做規則型預警，再做統計型預測，再做 AI 建議

優先分析主題：

- 庫存預警
- 工單成本差異
- 預算超支預警
- 供應商交期績效
- 銷售與需求預測

## 12. 主要風險與因應

### 12.1 風險

- 業務規則未明確，導致系統反覆返工
- 模組同步改動過大，導致整體不穩
- 流程配置化過快，造成治理失控
- 使用者訓練不足，導致新流程落地失敗

### 12.2 因應策略

- 以流程工作坊先釐清關鍵交易規則
- 採模組分批上線，不一次大切換
- 配置權限與版本控管同步建立
- 訓練、UAT、上線支持三者同步規劃

## 14. 結論

本 ERP 專案已具備成長為完整企業平台的骨架，但要達成高度流程整合、靈活擴展、組織採用與決策支持，必須從局部功能開發轉向系統性治理。

本藍圖的關鍵不是一次重寫，而是用清楚的邊界、可追溯的流程、可信的資料與分階段治理，讓系統逐步進化為真正可支撐企業營運的 ERP 平台。
