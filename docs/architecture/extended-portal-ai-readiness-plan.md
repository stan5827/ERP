# 延伸功能啟動與安全門檻規劃

> **評估日期：** 2026-11-05
> **範圍：** 供應商入口、請款 Portal 與 AI 整合
> **啟用原則：** 沒有完成產品政策核准、技術安全閘門及隔離環境驗收，不得對外開放或啟用正式資料。

## 一、建議優先序

| 優先序 | 功能線 | 啟動方式 | 主要依賴 |
|---|---|---|---|
| 1 | 供應商入口安全切片 | 啟動 OIDC／邀請、RFQ／PO／CAPA 隔離環境驗收 | Keycloak、DMZ/APISIX、供應商主檔、稽核 |
| 2 | 請款 Portal | 在供應商入口驗收後啟動財務政策與附件安全閉環 | 財務政策、三方核對、正式附件儲存與惡意程式掃描 |
| 3 | AI 整合 | 最後啟動限定唯讀 WIP PoC | 資料分類、模型出口、權限範圍、語意與答案驗證 |

供應商入口與請款 Portal 應共用相同身分、供應商範圍及稽核基礎。請款已實作 UI 與後端切片，但不得因為程式存在而視為可上線。AI 不得優先於 ERP 核心權限、稽核及資料分類建立完整控制。

## 二、供應商入口啟動門檻

### P0 政策核准

- 採購核准供應商資格、邀請者、停權／失效、重新邀請及共用 email 處理規則。
- 資安核准 Keycloak Realm、public client、PKCE、MFA、session lifetime、封鎖策略及異常登入處理。
- 網路團隊核准獨立 public origin、TLS、APISIX/DMZ 路由、WAF、來源限制、速率限制及內部管理介面隔離。
- 資料保留負責人核准附件、訊息、稽核與邀請紀錄保留期限及刪除流程。

### P0 技術與安全閘門

- 所有供應商 API 以獨立身份驗證 scheme 與 supplier binding 授權，不能接受請求 body 的 `SupplierId`。
- 供應商 `sub` 必須對應唯一啟用的 `SupplierUser`；停用帳號、供應商或未核准身分一律拒絕。
- 通過同供應商／跨供應商、員工／供應商、停權、過期邀請及撤銷 session 測試。
- 邀請、登入、授權、RFQ、PO 回覆、CAPA 與附件操作均保存操作者、時間、資源及結果稽核。
- 正式附件儲存、惡意程式掃描與 private object storage 已配置；未 clean 或掃描不可用時 fail closed。

### 驗收退出條件

- 隔離 UAT 完成 OIDC PKCE、MFA、邀請、停權、RFQ／PO／CAPA 的 Key User 驗收。
- 403／401／404 資料存在性行為符合預期，不洩露其他供應商資源。
- 採購與資安共同簽認後，才可考慮有限供應商灰度發布。

## 三、請款 Portal 啟動門檻

### 財務政策核准

- 財務核定發票號碼規則、幣別、稅額、計價精度、重複發票、差異容差及例外核准流程。
- 採購核定可請款來源：單一或多 PO、收貨／驗收單、已請款餘量及退貨扣抵規則。
- 財務核定支援的附件類型、大小、數量、掃描服務 SLA、保留期限及內部可見範圍。
- 内部責任核定送審、退回、拒絕、核准、取消及補件角色；不得由供應商直接建立正式 AP 或付款。

### 技術與會計閘門

- 發票送審修訂不可變；退回、補件及重送保留完整歷程與版本。
- 三方核對差異未經核准政策不得放行；稅額計算不得在前端自行決定。
- 核准必須冪等且在原子交易建立唯一正式 `AccountsPayable`；不得在送審草稿階段建立 AP。
- 核准不得建立付款批次、付款紀錄、會計傳票或付款承諾。
- 所有附件僅 private storage、clean 狀態可下載；掃描失敗、超時或服務不可用採 fail closed。
- 發票重複提交、併發版本衝突、內部／供應商權限及審核者偽造皆需自動化回歸測試。

### 驗收退出條件

- 隔離 UAT 完成正常請款、重送、退回、拒絕、重複發票、差異、附件惡意檔及重試核准情境。
- 正式 AP 只能由核准交易建立一次；核准後可追溯來源、操作者、修訂與原始附件。
- 財務、採購、資安共同簽認後才可小規模發布；未核准差異容差不得啟用自動核准。

## 四、AI 整合啟動門槛

### P0 政策核准

- 資料所有者核定允許送模型的資料類別；首期僅限已核准的 `internal`／去識別化製造資料。
- 資訊安全核准 provider、model、endpoint、保留期限、日誌、提示詞存取、刪除及模型供應商契約。
- 業務負責人核定首期問題、允許欄位、計算口徑、答案範圍及不可回答內容。
- 生產主管核定部門、成本中心、工作中心和工單資料範圍；缺少有效映射時全閉。

### P0 技術閘門

- LLM egress 預設停用；只允許伺服器核准的 loopback provider、model 與 endpoint。
- 禁止任何人員提供 `provider credentials`、任意 system prompt、任意 model 或任意外部 URL。
- 保持空的寫入工具 allowlist；工單、採購、庫存、發料、完工、核准等寫入工具不得由模型執行。
- ERP JWT 每回合重新檢查、權限與資料範圍不得由 prompt 或對話快取提升。
- 文字結果需與後端結構化 facts、FactId、單位及數字核對；不可靠答案不得顯示或標成成功。
- feature flag 預設關閉；僅 seed users 可灰度；提供 kill switch、撤權測試與回退演練。
- 禁止模型直接連 PostgreSQL、shell、瀏覽器、任意 HTTP、MCP 或其他未審核工具。

### 驗收退出條件

- 隔離資料完成換身分、撤權、跨部門、單位、數字、拒絕回答及模型改寫測試。
- 正常回答、拒絕回答與稽核紀錄皆可重現；Unavailability/Safety failure 不得偽裝成業務答案。
- 無安全、資料外送、scope 或 kill switch 缺陷時才灰度開放。

## 五、執行順序

### Wave 1：供應商入口

1. 彙整並核准 P0 攔門清單。
2. 完成正式 DMZ、OIDC、MFA、附件儲存與掃描設定。
3. 執行跨供應商越權、邀請生命週期、停權及附件安全回歸。
4. 完成採購／資安 UAT 簽認後灰度。

### Wave 2：請款 Portal

1. 財務確認稅務、容差、發票唯一性及來源規則。
2. 完成正式附件儲存、掃描與審核角色配置。
3. 執行送審、退回、重送、核准冪等及正式 AP 追溯測試。
4. 財務、採購及資安簽認後灰度；不啟用自動付款。

### Wave 3：AI

1. 確認資料分類、provider/model/endpoint 及責任人。
2. 保持唯讀 WIP 首期垂直切片，實作 feature flag 與 kill switch。
3. 執行權限、scope、數字、撤權、資料外送及答案誤導測試。
4. 生產／資訊安全共同核准後，再評估文件 RAG、草稿或人工核准寫入。

## 六、目前不應開放的項目

- Supplier Portal 公網直接暴露但沒有完成 DMZ、WAF、TLS、MFA 或跨租戶安全驗收。
- 請款草稿或核准建立正式 AP、付款、傳票或自動付款。
- AI 呼叫 provider 但未完成 egress allowlist、稽核、資料分類或白名單路徑。
- AI 開放工單、採購、庫存、發料、完工、核准等寫入工具。
- 使用供應商 Portal 身分直接映射員工 ERP 權限或跳過供應商範圍。

### 尚未達成的啟用 Gate

- 供應商入口尚未完成採購／資安對跨供應商越權、停權、MFA 及附件安全的完整 UAT簽認。
- 請款尚未取得財務對稅額、發票唯一性、差異容差及附件規則的正式核准，因此不得啟用正式送審。
- AI 尚未核准 provider、model、endpoint、資料分類及責任人，因此目前維持 feature disabled；不啟用外部 provider 或寫入工具。
