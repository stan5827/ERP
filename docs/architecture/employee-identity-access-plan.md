# ERP 系統權限與使用者管理規劃

> 狀態：規劃草案  
> 範圍：ERP 內部員工身分、帳號生命週期、RBAC 權限樹、職能分工及敏感人事資料存取  
> 依據：使用者提供的「ERP系統權限與使用者管理規劃.md」、本系統現有程式、資料模型及架構文件

## 1. 規劃目標

建立一套以員工為身分來源、以獨立登入帳號作為認證憑證、以角色組合權限的管理流程。員工異動、帳號狀態、登入授權與稽核紀錄應保持一致；角色權限採最小授權，並避免同一人取得互相牴觸的職務權限。權限樹需同時支援前端導覽及後端 API 授權，但前端隱藏選單或按鈕不視為安全控制。

此規劃以補齊及整合既有功能為原則，不另建一套 HR、登入或 RBAC 子系統，也不改變現有 API 的既有路由及回應格式；必要的授權變更須補相容性測試。文件是實作與業務核定依據，不代表目前功能已符合目標，也不授權直接在正式資料庫建立高權限帳號或批次變更既有角色。

### 2.1 本系統的邊界與安全基線

- 本規劃管理的是 ERP 內部員工帳號；供應商入口的 `SupplierUser` 等外部身分維持獨立，不套用「每位員工一個內部帳號」的唯一性規則。
- 一般內部員工帳號必須綁定一位在職員工；既有未綁員工的管理／維運帳號列為例外清冊，只有完成具名負責人、用途、替代方案及期限核准後才可暫留，不可把現有 `admin` 默認當成所有人員的身份。
- 權限管理採**預設拒絕**：未登入回 401，已登入但缺少所需權限回 403。只要 API 讀取或異動受保護資料，就必須明確有授權政策；僅有前端權限隱藏不合格。
- 首批修正須優先處理未授權的註冊與管理重設：註冊端點不得接受匿名呼叫者自行指定角色；管理重設不得使用程式內預設密鑰，也不得由匿名呼叫者觸發。
- `RoleName` 是顯示名稱，使用者的多角色權限取聯集，並對聯集執行 SoD 衝突檢查。依 2026-10-24 使用者核定的新政策，`Admin` 是明確的全系統最高權限角色，可跨模組執行緊急維護與營運對帳；所有 Admin 操作仍須留存稽核。此新政策取代本文件原先「Admin 不取得業務權限」的角色範本。
- 首次導入不能直接撤除現有管理入口或變更正式角色。先產出差異報告、保留受控救援方式、分模組導入並驗證；所有高風險政策須經系統負責人與業務權責主管核准。

## 3. 目標設計

### 3.1 身分與帳號

- `Employee` 是人事與組織歸屬的單一事實來源；`User` 是登入帳號，兩者分開管理。
- ERP 內部員工採「一位員工至多一個登入帳號」；員工可尚未開通帳號。所有既有帳號需先盤點重複或無效關聯，再新增唯一性限制。
- 帳號建立由具權限的管理人員執行，必須關聯有效員工，不開放匿名自助註冊。帳號名稱使用員工編號或公司 Email 的其中一種一致規則，建立前檢查重複；密碼以一次性、短效、單次使用的啟用連結設定，不由管理者代設或以一般訊息傳送初始密碼。
- 登入只允許啟用帳號且符合員工在職政策者；HR 停職／離職後，既有 Token 亦須失效，不只阻止下一次登入。
- 停用帳號不刪除員工、歷史單據、稽核紀錄或帳號關聯。復職應由授權流程重新確認帳號及角色，不自動恢復過期或不再適用的授權。
- 員工編號、姓名、部門及員工狀態由 HR 主檔提供；帳號 Email 預設帶入員工 Email，但若允許登入別名或通知信箱不同，須在帳號資料明確保存並記錄維護來源。
- 除經核准且有期限的維運／緊急帳號外，已啟用的內部人員帳號必須綁定唯一員工；未綁定帳號不得因其角色名稱為 `Admin` 而自動通過人員身分或製造作業驗證。

帳號開通流程：HR 建立或確認員工 → 系統管理者查詢未綁定且符合在職條件的員工 → 建立帳號並指派已核定角色 → 系統發送短效啟用連結 → 員工首次設定密碼並完成登入 → 管理者可查詢帳號、員工、角色與稽核軌跡。離職／停職由 HR 異動觸發停用與 Token 撤銷；調職則產生角色差異審查，不自動保留與新職務不符的授權。

### 3.2 員工資料分級

員工欄位維持在現有 HR 主檔，依用途劃分存取範圍：

| 資料分類 | 欄位例子 | 建議存取原則 |
|---|---|---|
| 組織與工作 | 員工編號、姓名、部門、職稱、職等、主管、到職日、狀態 | HR 維護；主管限所屬組織所需欄位；一般模組僅讀取業務必要的識別資訊 |
| 聯絡及緊急聯絡 | 電話、Email、地址、緊急聯絡人 | HR 維護；僅提供給有業務需要的角色 |
| 身分及法定資料 | 身分證／居留證、出生日期、投保級距、扶養人數 | 限 HR 指定職責；清單不得回傳完整值，明細採必要遮罩 |
| 薪酬與銀行 | 薪資、津貼、銀行帳號 | 另設薪資資料權限，不因持有一般 HR 角色而自動取得 |
| 系統帳號 | 帳號名稱、啟用狀態、最後登入、角色 | 系統管理者依職責管理；一般 HR 不可讀取密碼雜湊、Token 或認證秘密 |

員工主檔的 `Status` 沿用既有值並先盤點歷史資料；至少統一處理 `active`、`leave`、`terminated`，UI 顯示名稱可本地化。不得直接以刪除員工代替離職。

### 3.3 RBAC 與權限目錄

- 權限代碼採一致且穩定的 `module:resource:action` 格式，例如 `inventory:sku:view`、`hr:employee:update`、`hr:payroll:view`、`users:account:assign-role`。
- 動作至少涵蓋 `view`、`create`、`update`、`delete`、`approve`；依現存模組增加 `export`、`post`、`reverse` 等高風險操作。除經使用者核定的 `Admin` 全系統覆蓋外，其餘角色仍採明確模組範圍與最小特權。
- 權限樹分成導覽節點與授權葉節點：`menu`／`page` 用於選單和頁面導覽，`action` 才代表可被角色授予及 API 驗證的動作。父節點勾選只作為管理 UI 的批次選取，不得在授權時自動繼承或放大權限。
- API 路由、HTTP 方法與權限代碼的綁定由伺服器端政策明確宣告（例如端點上的授權屬性／政策名稱），不可只靠 `Permission` 資料列上的可編輯 URL 欄位決定安全規則。選單節點可保存前端路由，以供導覽使用。
- 目錄需具備唯一且不可隨意重用的 `PermissionCode`、顯示名稱／說明、模組、資源、動作、類型、父節點、排序、啟用狀態及必要的前端路由；代碼變更須以版本化對照與遷移處理。
- `Role` 是可指派的權限集合；`UserRole` 支援一帳號多角色。角色代碼應穩定、顯示名稱可調整，系統內建角色不可被刪除或改成不可預期的高權限。
- 每一項 API 授權由伺服器端執行。前端角色／權限只用於導覽與操作提示，不能作為資料保護邊界。
- JWT 權限宣告與資料庫授權必須有明確有效期／撤銷策略。角色或權限被撤銷時，既有 Token 不可繼續保有舊權限直到長效 Token 自然過期。
- 授權應可表達資料範圍，例如本人、所屬部門、全公司；本期優先完成 API 動作級授權，涉及薪酬、員工明細及部門主管查詢時同步定義其資料範圍，避免只做 UI 過濾。

權限撤銷建議以帳號 `AuthVersion`／security stamp 作為權威版本：JWT 帶入簽發版本，每次授權依目前版本拒絕舊 Token；可使用有明確最長有效時間和失效機制的快取減少查詢負載，但不得讓快取成為無上限延遲撤銷的理由。若改採短效 Token，須另有可驗證的撤銷時限及風險接受決議。

### 3.4 核定角色與舊角色處置

以下五類角色依 2026-10-24 使用者確認的政策作為實作基準；未列出的細部資源／動作預設拒絕，正式環境套用前仍須完成相關部門簽核。

| 角色名稱 | 核定範圍 |
|---|---|
| `Admin` | 全系統最高權限，包含財務、HR、業務交易的緊急維護與營運對帳；所有管理與交易操作須留痕 |
| `HR Manager` | 人事主檔、出勤考勤、請假審核及薪資核算；不授予生產與財務核心交易權限 |
| `Production Supervisor` | 工序報工審核、工單派工、BOM／ECN 審批及產線進度監控 |
| `Operator` | 由登入帳號帶入本人身分；僅可執行個人／班組報工與本人 ESS，不得代填他人身分或審核報工 |
| `Finance` | 應收應付、三方勾稽、實際成本結算及總帳查閱；總帳限查閱 |

不在上述五類中的既有角色一律標記為停用／Deprecated，保留歷史指派供追溯，但不再簽發其角色宣告或允許新指派。不得自動將舊角色映射到新角色；尚未重新指派新角色的帳號依 Default-Deny 拒絕受保護 API。角色重新指派必須由 Admin 提供原因，記錄前後角色與操作者，並遞增帳號 `SecurityVersion`。全系統 Admin 覆蓋不免除資料狀態、單據狀態或已存在的交易一致性檢查。

### 3.5 職能分工（SoD）

- 權限管理須有可維護、可稽核的衝突規則；指派新角色或修改角色權限前，檢查使用者合併後的有效權限，不只檢查單一角色。
- 初始衝突規則至少涵蓋：同一人不得建立並核准同一張單據；採購請購／採購建檔與其最終核准分離；付款建立／付款放行分離；供應商銀行資料維護與付款核准分離。
- 衝突規則適用於人員所有角色及主管代理期間。一般指派遇到衝突應拒絕並指出原因；緊急例外須具名核准、設定到期日、說明理由並留下稽核紀錄。
- 若 ERP 工作流程已儲存單據建立者，核准時還須檢查實際單據建立者，避免角色分離卻仍可自我核准。

## 4. 使用情境與驗收情境

### 情境 A：建立員工並開通帳號（P1）

HR 建立員工資料後，由獲授權管理者開通登入帳號並指派符合職務的角色。

- **Given** 員工資料有效且沒有既有帳號，**When** 管理者建立帳號並指派核定角色，**Then** 帳號關聯該員工、角色及建立者／時間均可稽核。
- **Given** 員工已有帳號或員工狀態不允許登入，**When** 嘗試再建帳號或啟用帳號，**Then** 系統拒絕並明確指出原因，不產生重複帳號。
- **Given** 一般使用者呼叫帳號建立或角色指派功能，**When** 請求到達 API，**Then** 伺服器拒絕未授權操作。

### 情境 B：員工離職、留停、調職及復職（P1）

- **Given** 員工被 HR 標記離職，**When** 離職異動完成，**Then** 關聯帳號停用，後續 API 請求被拒絕，歷史交易與稽核仍可查。
- **Given** 員工部門或職務變更，**When** 組織異動生效，**Then** 系統提供原角色、新職務建議角色及差異供授權人確認；舊角色不得無期限殘留。
- **Given** 員工復職，**When** HR 恢復有效在職狀態，**Then** 帳號不因復職而自動恢復所有舊角色，須依核准流程重新啟用。
- 留職停薪採停用登入與業務授權的預設政策；主管核准的特殊例外需記錄期限及理由。

### 情境 C：角色、權限與 SoD 管理（P1）

- **Given** 權限管理者建立或更新角色，**When** 選取權限，**Then** 顯示權限所屬模組、資源、動作及高風險標示。
- **Given** 更新角色會造成某使用者取得衝突權限，**When** 管理者儲存，**Then** 系統拒絕或進入核准的限期例外流程，且提供衝突清單。
- **Given** 角色權限被撤銷，**When** 使用者持有更新前簽發的 Token 呼叫受限 API，**Then** 撤銷依本規劃的有效性機制生效，不沿用過期授權。
- **Given** 生產環境發生緊急事件且一般授權流程無法及時處理，**When** 具名申請人取得不同人核准的限期緊急權限，**Then** 權限依核准期限自動失效，預設最長不得超過 2 小時，請求、核准、使用及回收均產生高優先稽核事件。
- **Given** 緊急權限申請人同時是唯一可用的核准人，**When** 提出緊急授權申請，**Then** 系統不得接受自我核准，並要求依核定程序進行雙人覆核或事後覆核。

### 情境 D：查閱人事及薪酬資料（P1）

- **Given** 使用者只有一般員工查詢權限，**When** 查詢員工清單或明細，**Then** 不回傳身分證、銀行帳號、薪資等未授權欄位。
- **Given** 使用者持有薪資檢視權限，**When** 查詢薪酬資料，**Then** 依授權資料範圍回傳必要欄位，並記錄敏感資料存取事件。
- **Given** 主管具有部門範圍的員工查詢權限，**When** 查詢員工清單或明細，**Then** 只能取得直屬及核定下屬部門的員工資料，且仍須符合欄位級權限。

## 5. 功能需求

- **REQ-001**：系統必須以員工主檔作為內部員工身份來源，支援員工無帳號、但不允許同一員工有多個有效登入帳號。
- **REQ-002**：系統必須由具備授權的管理者開通、停用及重新啟用帳號；匿名使用者不得註冊 ERP 內部員工帳號。
- **REQ-003**：系統必須保留員工、帳號、角色指派與交易歷史；離職不得以實體刪除方式處理。
- **REQ-004**：系統必須依員工狀態執行帳號登入及既有 Token 的有效性檢查，並定義 `active`、`leave`、`terminated` 的行為。
- **REQ-005**：系統必須支援每個帳號多角色、每角色多權限，以及管理員查詢有效角色與權限來源。
- **REQ-006**：系統必須以穩定且唯一的 `module:resource:action` 權限代碼管理授權，並對受保護 API 執行伺服器端驗證。
- **REQ-007**：系統必須對新增、修改、停用員工帳號、角色指派、權限變更、SoD 例外及敏感資料讀取留下操作者、對象、時間、結果及必要原因。
- **REQ-008**：系統必須對員工敏感資料提供職務分離、最小回傳、必要遮罩與欄位級權限控制；主管查閱員工資料時，必須限制在本人直屬及核定下屬部門範圍。
- **REQ-009**：系統必須在角色指派及角色權限修改時檢查跨角色的 SoD 衝突，並提供具期限、核准人與原因的例外程序；亦須支援緊急 Break-Glass 授權與自動失效。
- **REQ-010**：系統必須讓部門、職稱、職等與主管異動觸發角色審查，並可比較異動前後權限；不得默默沿用不適用的權限。
- **REQ-011**：系統必須保留既有 API 路由及回應封裝；新增授權限制時，對前端及員工 App 提供可預期的未登入／無權限回應。
- **REQ-012**：系統不得將明文密碼、密碼雜湊、JWT、完整身分證號、完整銀行帳號寫入一般應用程式日誌或稽核描述。
- **REQ-013**：系統必須提供緊急 Break-Glass 授權：申請人與核准人分離、具備用途及理由、明確到期時間（預設最長 2 小時）、到期自動撤銷及高優先稽核；不得以一般管理角色或永久性權限作為緊急替代。
- **REQ-014**：匿名使用者不得建立或重設 ERP 內部帳號；所有帳號、角色、權限管理 API 必須在伺服器端檢查專用授權，不能依賴前端隱藏介面。
- **REQ-015**：權限樹的選單／頁面節點不得自動授予資料存取權；權限代碼須明確映射到伺服器端端點政策，缺少政策的受保護 API 必須拒絕存取。
- **REQ-016**：角色、權限或帳號停用後，舊 JWT 的授權失效必須符合核定的最大撤銷時限；需有可測試的版本檢查或等效機制。

## 6. 主要資料實體

| 實體 | 現況 | 目標欄位／職責 |
|---|---|---|
| `Employee` | 現有 HR 主檔 | 沿用員工編號、姓名、部門、主管、狀態、人事與薪酬欄位；員工狀態是內部帳號可登入與否的來源 |
| `User` | 已有帳號、雜湊、可空 `EmployeeId`、`IsActive`、最後登入、強制改密碼欄位 | 沿用 `Id`、`Username`、`Email`、`EmployeeId`、雜湊及時間欄位；增補登入失敗次數、鎖定期限、`AuthVersion`／security stamp、建立者／更新者。以有效帳號唯一索引確保一員工最多一帳號；先清理重複與核准未綁定例外 |
| `Role` | 已有 `RoleName`、`Description`、`IsSystem` | 增補穩定且唯一的 `RoleCode`、啟用狀態及更新稽核；顯示名稱可改，代碼不可任意重用 |
| `Permission` | 已有唯一 `PermissionCode`、`ModuleName`、`ActionType`、`PermissionType`、`ParentId`、`Description`、`SortOrder`、`IsActive` | 保留現有欄位並以明確命名規則維護代碼；menu/page 可加前端路由識別，action 綁定伺服器端授權政策；不依賴可編輯 URL 做後端授權 |
| `UserRole` | 現有多對多關聯及唯一組合索引 | 保留目前有效關聯；若需要指派者／期限／來源，新增有效授權歷程實體或欄位並記錄授權、撤銷原因與時間，不覆寫掉歷史 |
| `RolePermission` | 現有角色－權限多對多關聯及唯一組合索引 | 角色權限異動採交易處理並記錄異動前後差異；系統內建角色不得刪除或無痕升權 |
| SoD 規則／例外 | 尚待落地 | 規則描述互斥權限或業務職責；例外需核准人、申請人、原因、生效／到期時間及定期覆核 |
| Break-Glass grant | 尚待落地 | 獨立於一般角色的緊急權限紀錄，含具名申請人、不同核准人、理由／事件、最小權限、到期與覆核 |
| `AuditLog` | 已有稽核實體及部分 API／資料異動攔截 | 擴充可查詢的帳號、角色、權限、登入拒絕、角色指派及敏感資料事件；排除密碼、Token、完整個資與秘密 |

資料庫變更採增量 EF Core migration；新增員工帳號唯一約束前，先報告及處理既有重複 `EmployeeId`，不直接刪除或合併資料。帳號鎖定／稽核事件若需高頻查詢，才另建專用實體，不將密碼歷程搬到一般稽核描述欄位。若既有外部 Portal 帳號共用 `Users` 表或使用相同認證管線，須先盤點帳號類型再套用員工唯一性限制。

### 6.1 目標欄位與約束

下列欄位是規劃目標，不要求一次增加全部欄位；先盤點並沿用既有同義欄位，僅以增量 migration 補缺。所有時間以 UTC 儲存、前端依使用者時區顯示。

| 實體 | 欄位 | 必填／約束 | 說明 |
|---|---|---|---|
| `User` | `Id`、`Username`、`PasswordHash` | 主鍵；Username 必填且唯一；PasswordHash 必填 | 不保存明文密碼；登入名稱採全系統一致大小寫／正規化規則 |
| `User` | `EmployeeId` | 一般內部帳號必填；有效員工關聯唯一 | 例外管理帳號另有核准清冊；若存在外部帳號共用資料表，先拆分類型後再建立條件式唯一索引 |
| `User` | `Email`、`IsActive`、`MustChangePassword` | Email 依通知／登入政策驗證；布林必填 | 員工主檔為 Email 預設來源；停用帳號保留交易與審計資料 |
| `User` | `FailedLoginCount`、`LockoutEnd`、`AuthVersion` | 必填；失敗次數非負 | 暫時鎖定與舊 JWT 撤銷；每次密碼重設、停權或權限撤銷時增加授權版本 |
| `User` | `LastLoginAt`、`CreatedAt`、`UpdatedAt`、`CreatedBy`、`ModifiedBy` | 建立／異動時間及操作者需可追溯 | 不將 Token、密碼或敏感憑證放在通用 DTO |
| `Role` | `Id`、`RoleCode`、`RoleName` | 主鍵；RoleCode 必填且唯一；顯示名稱必填 | `RoleCode` 為穩定識別；RoleName 可本地化或調整 |
| `Role` | `Description`、`IsSystem`、`IsActive`、異動欄位 | IsSystem／IsActive 必填 | 系統角色有不可刪除／不可自我升權保護 |
| `Permission` | `Id`、`PermissionCode`、`ModuleName`、`ActionType`、`PermissionType` | 權限代碼唯一；其餘必要欄位必填 | 授權動作使用 `module:resource:action`；類型沿用 `menu`、`page`、`action` |
| `Permission` | `ParentId`、`FrontendPath`、`Description`、`SortOrder`、`IsActive` | ParentId 可空；禁止循環參照 | `FrontendPath` 僅供選單／頁面導覽；不作 API 存取控制依據 |
| `UserRole`、`RolePermission` | 關聯主鍵及兩端 FK | 組合唯一；外鍵有效 | 使用資料庫交易更新關聯；授權和撤銷另留歷程與操作者 |
| `UserActivationToken`（新增） | `UserId`、`TokenHash`、`ExpiresAt`、`UsedAt`、`CreatedAt` | TokenHash 唯一；原始 Token 不落庫 | 一次性、短效啟用／重設憑證；使用後不可重放 |
| `UserRoleAuditEvent`（可沿用 AuditLog 或新增） | 對象使用者、角色、操作者、動作、原因、時間、差異 | 管理操作必須完整留痕 | 依稽核查詢量與既有 AuditLog 能力決定是否獨立建表 |

## 7. 分期執行計畫

### Phase 0 — 權限盤點與基線

1. 盤點所有 Controller／API、既有 `[Authorize]`、`PermissionAuthorizeFilter` 的實際套用點、匿名端點及前端／行動 App 呼叫。
2. 核對 `UsersController`、`RolesController`、`PermissionsController`、`SystemSettingsController` 路由，列出前端已呼叫但後端尚未實作的使用者角色指派、角色建立與角色權限更新端點。
3. 建立模組－資源－動作權限目錄及角色權限矩陣；列出未受保護、無對應權限代碼及 `Module.Action`／`module:resource:action` 衝突。
4. 盤點既有帳號的 `EmployeeId` 重複、孤兒帳號、外部／維運帳號、系統管理帳號、失效角色與重複／未用權限；分別對照每個環境的資料，不假設主機與 Docker 資料一致。
5. 明確定義員工狀態對登入及 Token 的影響，確認 SoD 初始衝突矩陣及例外核准人；先列出敏感人事欄位會由哪些 API、列表及匯出回傳。
6. 各權責主管以正式簽核表或具名會議決議核准權限矩陣、資料範圍及 SoD／Break-Glass 流程；保存版本、生效日、核准人與變更責任人。

**完成門檻：** 有可審閱的 API 權限矩陣、資料盤點報告及角色初始矩陣；每個受影響模組均有正式核准證據。未核准模組不得進入後續權限 migration；未確認的業務權限不以管理員全權替代。

### Phase 1 — 帳號安全與員工生命週期

1. 先以授權屬性封鎖匿名內部帳號建立與密碼重設，再將帳號建立移至受保護的使用者管理流程；保留舊路由時，必須安全拒絕匿名請求並維持可預期 API 回應。
2. 移除程式內可預測的管理重設密鑰 fallback；管理重設改為具專用權限、重設後強制改密碼、撤銷舊 Token 及完整稽核的操作。
3. 在盤點與清理重複關聯後，新增有效員工狀態檢查及一員工至多一個有效帳號的資料庫唯一限制；未綁定管理／維運帳號需先完成例外審核，不可直接讓 migration 失敗或自動綁到任一員工。
4. 員工停職／離職時以同一個可復原交易停用登入、更新授權版本並留下稽核；部門／職務異動產生角色差異待辦，不自動授予新權限。復職需重新審核並啟用。
5. 新增登入失敗次數、暫時鎖定及受控解鎖政策；登入回應維持現有前端和 App 所需欄位。密碼重設使用一次性短效憑證，不把密碼或 Token 寫入日誌。

**完成門檻：** 離職停權及 Token 撤銷的整合測試通過；任何管理重設操作均需授權、稽核及受控秘密來源。

### Phase 2 — 權限目錄、角色管理與 SoD

1. 定義並核准 `PermissionCode` 字典及舊代碼對照；以資料遷移統一格式，確保已簽發 JWT、現有 UI 與模組 API 在相容期不會因格式切換被意外放行或鎖出。
2. 實作現有 System Settings UI 所需的使用者／角色／權限管理端點，至少包含使用者查詢與開通、角色指派、角色 CRUD、角色權限查詢／更新及權限樹維護；全部由 Service 介面處理並以資料庫交易保存。
3. 權限目錄驗證唯一代碼、合法父節點、禁止自我／循環參照、有效父節點與必要欄位；被角色使用的權限停用時採軟停用並報告影響，不無提示硬刪除及移除關聯。
4. 對系統角色採保護措施，將高風險權限變更限定給指定管理者；記錄異動前後差異、操作者、時間、原因及受影響帳號。
5. 加入角色合併後 SoD 衝突檢查、單據建立者與核准者分離、例外到期與定期覆核；一般 SoD 例外與 Break-Glass 緊急授權分開建模及稽核。
6. 以模組為單位將 API 由明確盤點的舊授權轉為伺服器端政策；管理端點和高風險寫入／核准端點優先採預設拒絕。前端依登入帳號的有效權限呈現操作，但不可替代 API 判斷。

**完成門檻：** 角色／權限管理端點不再是 stub；正向、未登入、無權限、衝突授權及例外到期測試均通過。

Break-Glass 使用獨立的最小權限、具名申請及不同人核准流程，預設最長 2 小時，於到期時自動撤銷；每次使用均留下高優先稽核事件並通知覆核人。不可自我核准；無法取得第二位核准人時，只能依核定的雙人控制或事後覆核程序處理，且不得留下永久權限。

### Phase 3 — 管理介面、資料保護與遷移

1. 在現有前端 HR／系統管理介面加入帳號清單、帳號開通／停用、角色核派、角色權限矩陣及 SoD 衝突提示；Break-Glass 管理介面待 Phase 4 核准後才啟用。
2. 讓前端與員工 App 改以登入者有效權限及目錄樹過濾選單、頁面和操作，不再以第一個角色名稱或固定全開模組清單推導授權。
3. 將員工敏感欄位拆分至明確權限，不再在通用 HR 明細或列表中無條件回傳。
4. 對既有使用者、角色及權限執行可重複、可檢核的遷移；先輸出將被停權、失去角色或需人工決定的差異報表，獲核准後再套用。
5. 以相容方式部署 API、前端與 migration；提供回滾步驟及操作人員通知，並確認員工 App 不因權限回應變更而失效。

**完成門檻：** 管理介面操作和 API 權限一致；敏感欄位不可由低權限使用者透過 API、匯出或清單繞過；遷移可重跑且結果一致。

### Phase 4 — 權限治理深化與正式上線

1. 依模組主管核准的矩陣逐一完成 API 授權覆蓋及冒煙測試；確認任何受保護端點都不會因漏設 Filter／Attribute 而匿名可用。
2. 擴充 SoD 規則、具期限例外及定期覆核；Break-Glass 僅在核准人、通知、到期撤銷及事後覆核流程可運作並經演練後啟用。
3. 驗證角色或帳號停用後舊 Token 的失效時限、稽核告警及救援管理流程；`Admin` 雖具核定的全系統權限，仍須受帳號／員工狀態檢查並完整留痕，不得以永久例外繞過安全檢查。
4. 以測試帳號完成 HR 建檔／帳號開通／首次登入／角色授權／拒絕無權限操作／離職停權／復職重審的端到端驗收，再分批正式啟用。

**完成門檻：** 全模組權限矩陣獲核准，所有高風險路由通過拒絕測試；移轉、復原及緊急停權演練通過。未完成核准的細部模組權限對一般角色維持 Default-Deny；Admin 僅依核定的全系統權限與完整稽核原則操作。

- 保留現有 `/api/erp/auth/login`、`/api/erp/auth/change-password`、`/api/erp/employees`、`/api/erp/users` 路由及既有回應封裝；`/api/erp/auth/register` 不得再作匿名內部帳號建立入口。
- 優先完成前端已使用的 `/api/erp/system-settings/users`、`/api/erp/system-settings/roles`、角色權限與使用者角色指派契約；盤點後決定 `/api/erp/roles`、`/api/erp/permissions` 是轉呼叫相同 Service 的相容別名，或在明確遷移客戶端後退役，不能形成兩套不同授權規則。
- `/api/erp/system-settings/role-modules/{roleName}` 不得以任意輸入角色名稱回傳硬編碼全模組權限；改以登入者身份取得有效權限與導覽資訊，並由伺服器授權政策獨立控管 API。
- 員工離職／復職使用現有員工端點，與帳號停權同步；帳號停用不得刪除關聯歷史。
- 所有受保護端點有明確授權需求；未指定權限代碼不得默認公開放行。管理、角色權限修改及高風險審批端點採預設拒絕。

### 必要測試

- **服務單元測試：** 員工狀態轉換、帳號建立及唯一性、角色合併、SoD 矩陣、敏感欄位映射。
- **整合測試：** 匿名註冊／重設被拒絕、未登入、有效角色、無權限、停用帳號、離職後舊 Token、撤銷角色後舊 Token、系統管理端點授權、API 回應相容及 migration。
- **權限樹測試：** 父節點不授予權限、已停用權限不會簽入有效權限、循環父節點／重複代碼無法建立、未綁授權政策的受保護端點被拒絕。
- **架構測試：** Controller 依賴 Service 介面；資料存取留在服務／基礎設施層；新增服務有 DI 註冊。
- **前端測試：** 依權限顯示／隱藏功能、管理操作成功與拒絕訊息、登入狀態過期後導回登入。
- **稽核測試：** 驗證角色／權限／帳號異動及敏感讀取可追溯，且日誌不含密碼、Token 或完整敏感值。

## 9. 成功標準

- **SC-001：** 每個可登入的內部帳號都能追溯至唯一員工；重複員工帳號建立成功數為 0。
- **SC-002：** 員工停用或離職生效後，該帳號下一次 API 請求即遭拒絕；停權不刪除其歷史交易或稽核資料。
- **SC-003：** 100% 的受保護 API 有對應伺服器端授權規則；未登入或無權限的測試請求均無法讀取或異動受保護資料。
- **SC-004：** 100% 的角色、權限、帳號狀態變更及 SoD 例外均可追溯至操作者、時間、對象與結果。
- **SC-005：** 未授權員工查詢不會取得身分證件、薪資或銀行帳號；所有明確授權的敏感讀取均可稽核。
- **SC-006：** 所有核定的 SoD 衝突組合均在指派或權限變更時被拒絕，或進入有期限、理由及核准人的例外流程。
- **SC-007：** 現有登入、HR、員工 App 及交易流程的回歸測試通過，既有 API 路由與回應格式未遭破壞。
- **SC-008：** 所有 Break-Glass 權限均有不同人核准、用途、理由與到期時間，且不得晚於核准後 2 小時失效；所有申請、核准、使用、撤銷及到期事件均可稽核。
- **SC-009：** 主管查詢員工資料時，結果僅包含本人直屬及核定下屬部門員工；跨部門或非授權欄位資料外洩測試結果為零。
- **SC-010：** 匿名帳號建立／管理重設成功數為 0；非具管理權限帳號存取所有帳號／角色／權限管理端點均收到 403。
- **SC-011：** 所有選單及頁面節點本身不授予 API 動作權限；授權矩陣中每個 action 權限均可追溯到實際伺服器端端點或明確業務政策。
- **SC-012：** 角色／帳號停用後的舊 JWT 在核定撤銷時限內失效；不得以只清除瀏覽器 localStorage 作為撤銷證明。

## 10. 假設與待確認事項

1. 本規劃處理 ERP 內部員工，不包含供應商／客戶 Portal 帳號及外部身份提供者整合。
2. 預設一位員工至多一個 ERP 登入帳號；若公司存在共用操作帳號或跨法人多帳號需求，需另行確認並採明確例外，不可默認解除唯一性。
3. 留職停薪預設停用登入；特殊職務例外須有期限、核准人及稽核記錄。
4. 權限代碼採 `module:resource:action`；建立正式角色權限矩陣前，由 HR、財務、採購、倉儲、生產、品保、業務及系統負責人核定每個操作的授權範圍。
5. 身分證、薪資及銀行資料沿用現有 HR 主檔，不代表所有 HR 角色皆可讀取；需由企業資料管理者確認保存期限與遮罩政策。
6. 系統程式目前可見的是記憶體快取註冊及 Redis optional 註解；Redis 是否已部署、可用及支援跨節點一致性須先驗證，不能假設 Redis 已是授權事實來源。
7. 緊急 Break-Glass 授權預設最長 2 小時；若企業內控要求更短，採更短期限；不得未經正式核准而延長。
