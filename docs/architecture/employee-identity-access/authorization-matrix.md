### 角色政策基準（使用者已核定；正式環境簽核欄位仍待補齊）

| 角色 | 核定授權範圍 | 明確限制 |
|---|---|---|
| 系統管理員（Admin） | 全系統最高權限，包含財務、HR、業務交易的緊急維護及營運對帳；帳號開通、員工綁定、角色指派與系統參數管理 | 管理及交易操作均須留存操作者、時間、前後值及原因；仍須遵守員工狀態、資料完整性與單據狀態檢查 |
| 人資主管（HR Manager） | 人事主檔、出勤考勤、請假審核及薪資核算 | 不授予生產與財務核心交易權限；ESS 僅能查本人資料 |
| 生產主管／廠長（Production Supervisor） | 工序報工審核、工單派工、BOM／ECN 審批及產線進度監控 | 不取得系統管理、人資或財務權限 |
| 一線作業員（Operator） | 由登入帳號帶入本人身分；個人報工、班組共同報工及本人 ESS | 不得選取或代填其他員工身分；不得讀取非本人 ESS 資料或執行主管核准 |
| 財務與會計（Finance） | 應收應付、三方勾稽、實際成本結算及總帳查閱 | 總帳限查閱；不得取得人資或生產管理權限 |

不在這五類中的既有角色統一停用／Deprecated，保留歷史 UserRole 關聯供追溯，不自動映射或重指派；沒有任何有效新角色的帳號對受保護 API 一律 Default-Deny。未明確授予某角色的其他模組僅 Admin 可使用。

此為角色邊界核定，不代表每個 API 的 `module:resource:action`、資料範圍、欄位遮罩及 SoD／Break-Glass 規則已逐項簽核；正式環境放行仍須補上權責主管、版本、生效日及簽核證據。

### 每次請求的授權安全條件

- 受保護 API 每次請求均須即時核對帳號啟用狀態、員工綁定／狀態、安全版本，以及資料庫中的目前角色與授權綁定；查詢失敗、缺少綁定或資料不一致時一律拒絕（fail closed）。
- 角色或權限指派異動須遞增 `SecurityVersion`，使既有 Token 於下一次請求失效；不得只依賴 JWT 內的舊角色 claims 授權。
- 未明確列入匿名白名單且未取得所需模組權限的 API 預設拒絕。
- 每次 JWT 請求核對資料庫中的有效角色綁定與 Token role claims；MVC API 另由全域權限篩選器根據 `module:action` 權限檢查，未配置或未映射一律拒絕。Admin 有全域最高權限；管理角色、使用者、權限樹及管理員密碼重設仍要求 Admin。角色異動需要原因、寫入稽核並遞增受影響帳號的 `SecurityVersion`。
- 2026-10-26 部署已建立 307 個冪等權限節點，支援三層模組／頁面／動作、父子勾選與半選、繁體中文標籤、目前登入者選單權限及 30 秒／視窗焦點刷新。新增的權限節點不會自動授予既有角色；Admin 必須先為角色設定已核准的權限，再指派角色給員工帳號。
- 目前不含資料列／欄位級限制、SoD 與 Break-Glass。上述角色政策矩陣是授權配置依據，應在正式使用前由 HR、財務及各模組負責人覆核；尚未核准的權限不得配置。

## 2026-10-26 RBAC 部署記錄

- 5173 的前後端已更新；PostgreSQL 資料庫與其他 Compose 服務未重建或重啟。`PermissionCatalog` 首次啟動會冪等建立 307 個節點。
- Default／Fallback Policy 改為要求已登入帳號；全域 `PermissionAuthorizeFilter` 對控制器 API 執行資料庫權限檢查，無模組映射或無權限回傳拒絕。`Admin` 保留全域 bypass；登入、密碼變更、查詢本人模組權限及明確匿名端點採最小必要例外。
- 既有角色不會自動取得權限。部署後，除 Admin 外的使用者需先由 Admin 指派已核准的角色權限；不可為方便而授予整個模組，除非授權矩陣已核准。
- 目前角色權限編輯器未內建角色專屬 allow-list／SoD 限制；Admin 的儲存操作仍須依此矩陣覆核。管理員密碼重設沿用 `ADMIN_RESET_SECRET`、密碼歷史檢查、強制下次登入變更及 `SecurityVersion` 撤銷。
- 未新增欄位／資料列範圍控制；模組動作授權不能取代各業務服務對本人資料、部門範圍及單據狀態的驗證。

## 員工狀態與登入政策

| 員工狀態 | 登入是否允許 | 既有 Token 撤銷時點 | 帳號處理 | 角色處理 | 核准人／依據 |
|---|---|---|---|---|---|
| 在職／active | 是 | 狀態異動時遞增 SecurityVersion，下一次請求失效 | 維持啟用 | 保留既有角色；部門／職稱變更不自動授權 | 使用者核定工程政策；正式 HR 簽核待留存 |
| 留停／leave | 是，僅允許 GET 本人 ESS | 狀態異動時遞增 SecurityVersion，下一次請求失效 | 維持已啟用帳號供 ESS 使用 | 不變更角色 | 使用者核定工程政策；正式 HR 簽核待留存 |
| 離職／terminated、停用／inactive | 否 | 狀態異動時遞增 SecurityVersion，下一次請求失效 | 同次儲存停用關聯帳號 | 保留歷史指派，不自動復職 | 使用者核定工程政策；正式 HR 簽核待留存 |
| 復職／rehire | 員工狀態恢復 active；帳號仍停用則不得登入 | 復職時遞增 SecurityVersion | 不自動重新啟用 | 不自動恢復或重算角色 | 使用者核定工程政策；正式 HR 簽核待留存 |

> 本表記錄本次實作採用的員工狀態政策；逐模組細項、SoD 與 Break-Glass 仍待各權責單位正式簽核。`leave` 本人 ESS 僅提供薪資、出勤、請假紀錄的 GET 查詢。

## Break-Glass 緊急授權

以下為待核定控制項，不代表已授權或已實作：

- 申請須具名、理由、事故／工單編號、最小權限及明確到期時間。
- 核准人不得與申請人相同；核准責任、是否允許事後覆核及通知對象待核定。
- 提案預設最長 2 小時；如企業內控要求較短，採較短期限；不得未經正式核准延長。
- 申請、核准、使用、撤銷、到期均須產生高優先稽核事件。

| 項目 | 核定內容 |
|---|---|
| 可申請人與適用情境 | 待核定 |
| 核准角色及雙人／事後覆核政策 | 待核定 |
| 可授予的最小權限集合 | 待核定 |
| 授權期限（建議不超過 2 小時） | 待核定 |
| 到期撤銷、通知與稽核保存期限 | 待核定 |

## Phase 2 放行條件

1. 受影響模組逐項完成權責主管簽核；角色、`module:resource:action`、資料範圍及敏感欄位不得留白。
2. HR 簽核在職、留停、離職、復職政策；系統／資安與業務共同簽核 Token 撤銷方式。
3. 各模組簽核 SoD 衝突與例外流程；系統／資安簽核 Break-Glass 核准、期限及稽核要求。
4. 資料預檢報告已產出，異常逐筆有處置核准；任何未核准異常不得自動修復或新增唯一約束。
5. 成功登入與有效授權請求的延遲基線及效能預算已核定。
