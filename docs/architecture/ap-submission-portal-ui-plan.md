# 供應商 Portal 請款送審操作介面規劃

> **狀態：** 首版前端已實作；瀏覽器／端到端驗收與對外啟用仍待完成
> **適用應用程式：** `src/erp-supplier-portal/`
> **依據：** [AP Submission API 規格](./ap-submission-api-spec.md) 與既有 Portal OIDC、RFQ、PO、CAPA 操作模式

## 1. 目標與範圍

讓已登入供應商可以從核准且已收貨／驗收的 PO 建立請款草稿，提交發票資料和憑證、追蹤審核結果及補件。前端只呼叫供應商 Portal API；供應商範圍、有效來源、發票唯一性、金額驗證、附件掃描與 AP 核准均由後端決定。

### 本階段納入

- 請款案件清單、狀態篩選、分頁及案件明細。
- 從可請款 PO／收貨單選取來源，建立並更新完整資料的草稿。
- 上傳、查看掃描狀態、下載及撤銷符合狀態規則的附件。
- 提交、取消草稿／退回案件、查看退回原因及審核歷程。
- 使用 API 回傳的版本進行 `ETag`／`If-Match` 樂觀併發控制；建立草稿使用 `Idempotency-Key`。
- 清楚說明核准不代表已付款；目前不顯示未串接的付款進度或預計匯款日。

### 本階段不納入

- 內部財務／採購審核介面。
- 付款進度、銀行帳務、電子發票平台、稅額自動試算或外幣轉換。
- 例外核准、差異容差調整，以及多 PO／多收貨單合併請款。
- 未經確認的正式附件儲存／掃描設定及 Portal 公開啟用。

## 2. 現況與前端整合依據

- Portal 是獨立 SPA，有自己的 Keycloak OIDC 工作階段、React Router、API client 與供應商身分顯示；不能使用員工 ERP 前端路由或員工 token。
- 目前已實作 RFQ、PO、CAPA 頁面，採側欄導覽、頁首、panel、表格、狀態標籤、載入／錯誤／空資料狀態及繁體中文文案。
- AP Submission API base path 為 `/api/supplier-portal/ap-submissions`，可由現有 `VITE_API_BASE_URL`（預設 `/api/supplier-portal`）及 Vite proxy 呼叫。
- 目前 API client 的共用 request helper 回傳 JSON／Blob，但不回傳 response headers；需要增補可保留 `ETag` 的 typed response 能力。
- API 的案件 detail DTO 提供目前修訂、附件及審核歷程，不提供所有舊修訂的完整欄位快照。首版只呈現目前版本及審核事件，不提供舊版本內容比較。
- API 不提供案件統計摘要，也不提供已核准 AP 的付款查詢。清單 KPI 不可用目前頁面筆數假裝全域統計。

## 3. 導覽與頁面資訊架構

新增側欄項目「請款送審」，位置建議接在「採購訂單」之後：

| 路由 | 頁面 | 目的 |
|---|---|---|
| `/ap-submissions` | 請款案件清單 | 查看案件、狀態、發票及目前審查結果。 |
| `/ap-submissions/new` | 建立請款草稿 | 選取可請款來源，填寫發票資料並建立草稿。 |
| `/ap-submissions/:submissionId` | 案件明細／補件 | 查看目前版本、附件、審核原因與歷程；依狀態提供可執行動作。 |

未登入者由既有 `RequireAuth` 保護；路由只是導覽與 UX，不是資料授權邊界。`sales` 角色可顯示建立、編輯、提交、取消等操作；其他角色可依案件讀取權限顯示唯讀頁面，但所有寫入仍以 API 授權結果為準。

## 4. 核心操作流程

### 4.1 建立請款草稿

1. 供應商進入「新增請款」，呼叫 `GET /eligible-sources`。
2. 選取 PO／收貨單；來源列顯示品號、已驗收數量、已請款數量、可請款餘量、單位、PO 單價及幣別。
3. 只允許從伺服器回傳的來源列建立請款明細；數量不得超過 API 回傳餘量。來源資訊不接受使用者自行輸入或覆寫 PO／收貨識別。
4. 填入發票號碼、日期、發票未稅／稅額／含稅總額，以及每列請款數量、發票單價與金額。幣別鎖定為 PO 幣別；UI 檢查精度及總額／明細加總一致，不自行推算稅率或匯率。
5. 使用明確按鈕建立草稿。**目前 API 建立草稿時要求完整發票欄位、至少一筆有效明細及精確加總**；「草稿」不是空白或部分填寫的自動儲存表單。送出前清楚說明資料將建立為可編輯草稿。
6. `POST /` 附 `Idempotency-Key`；成功後保存案件 ID、版本及 `ETag`，導向案件明細並提醒接續上傳憑證。

### 4.2 上傳憑證並提交

1. 進入 draft／returned 案件後，顯示至少一份 clean 附件為提交條件。
2. 支援 PDF、JPEG、PNG；前端可先做檔案大小／格式提示，但後端簽章驗證與惡意程式掃描才是最終判定。沿用目前政策上限：單檔 20 MB、每案件最多 10 個有效附件。
3. 上傳顯示進行中、掃描中、clean、rejected／掃描失敗等狀態；只有 API 回傳 clean 的附件可作為提交憑證。不可把 `422` 惡意檔或 `503` 掃描服務不可用顯示成上傳成功。
4. clean 檔案可由後端串流下載；僅在未提交且 API 允許時顯示撤銷按鈕。提交後附件不可替換或撤銷。
5. 提交前顯示來源、明細與金額檢查摘要，明確告知差異可能導致無法核准；送審至少需要一份 clean 附件。
6. `POST /{submissionId}/submit` 附目前 `If-Match`。成功後更新版本並切換唯讀審查狀態；若請求結果不明，先重新載入案件，不直接建立新案或盲目重送。

### 4.3 退回補件、取消與追蹤

- `returned` 顯示內部退回原因、目前修訂與可編輯欄位；第一次修改已提交內容會由後端建立新修訂。供應商應先更新資料、補上當前修訂附件，再以最新版本重送。
- draft／returned 可取消，取消對話框提供可選原因並要求確認；以 `If-Match` 傳送版本。
- `submitted` 顯示待審狀態及只讀資料，不顯示編輯、附件撤銷或取消按鈕。
- `approved` 顯示 AP 編號及核准日期（API 有回傳時），並明示「已核准，付款狀態請依後續正式付款資訊確認」；不推測匯款時間。
- `rejected`／`cancelled` 為終態，只提供案件與歷程唯讀檢視。
- 審核歷程以 API 回傳的 action、時間、供應商可見原因及核對結果呈現；不顯示 reviewer ID、物件儲存 key 或內部備註。

## 5. 畫面規格

### 5.1 清單

- 頁面標題、簡短說明及「新增請款」主按鈕。
- 篩選：案件狀態、發票日期起訖、案件編號；依 API 分頁，前端不一次載入全部紀錄。
- 欄位：案件編號、供應商發票號碼、發票日期、幣別／含稅總額、狀態、核對結果、送出／建立時間、檢視操作。
- 狀態使用文字加色彩標籤，不只用顏色表意；提供載入中、空清單、無篩選結果、錯誤及重試狀態。
- `approved` 可顯示正式 AP 編號時，從案件明細呈現；不將案件總額解讀為應付餘額或已付款金額。

### 5.2 建立／編輯表單

- 以清楚的步驟區塊呈現「選來源 → 發票與明細 → 建立草稿 → 憑證與送審」；因 API 需完整資料，前兩步完成前不可呼叫建立草稿。
- 必填欄位、數字精度、表頭加總與明細加總錯誤須在對應欄位附近呈現，並保留使用者輸入。
- 發票號碼重複以後端 `409` 為準；UI 不自行實作唯一性規則，以免與伺服器正規化不一致。
- 價格／數量／稅額差異要以清楚的警示列出，不套用未經核准的容差或稅率。差異是否可送審以 API 結果為準，核准仍可能被後端阻擋。
- 避免切換來源時靜默丟棄已輸入內容；變更來源前提供確認，且重新取得該 PO／收貨單可用明細。

### 5.3 案件明細

- 頁首顯示案件編號、狀態、目前版本與主要可用操作。
- 區塊順序：發票摘要、PO／收貨來源、請款明細、三方比對提示、附件、審核回覆／歷程。
- 案件狀態與伺服器 `matchResult`／`discrepancies` 一併呈現；差異顯示穩定代碼的友善繁中標籤，未知代碼保留安全的一般提示，不以解析代碼推算金額。
- 只有案件 API 回傳的欄位可顯示；供應商端不顯示內部審核者 ID、權限、儲存 key 或其他供應商資料。

## 6. API 與前端 client 工作項目

| 順序 | 變更 | 契約／注意事項 |
|---|---|---|
| 1 | 新增 AP Submission TypeScript 型別 | 對應 page、summary、detail、eligible source、draft request、result、attachment、review；避免 `any`。 |
| 2 | 擴充 API client methods | 對應清單、來源、建立、明細、更新、提交、取消、附件清單／上傳／撤銷／下載；路徑參數均 encode。 |
| 3 | 保留 response metadata | 新增可回傳 body + `ETag` 的 request helper 能力；更新、提交、取消使用 `If-Match`，不從 body 版本取代 header 契約。 |
| 4 | 建立冪等建立請求 | 每一次新的建立意圖產生 UUID `Idempotency-Key`。相同 payload 的可重試請求重用該 key；不同 payload 必須使用新 key。網路結果不明時先查案件清單／重載，避免直接產生另一個 key 再建重複案。 |
| 5 | 表單與狀態管理 | 只有使用者明確儲存／建立草稿時呼叫 API；不宣稱尚未送至 API 的輸入已自動儲存。 |
| 6 | 統一錯誤呈現 | 保留 `PortalApiError.status` 並依 401／403／404／409／413／422／503 提供安全、可行動訊息；409 重新載入以取得最新 ETag。 |
| 7 | multipart 附件處理 | 不手動設定 multipart `Content-Type`；檔案下載沿用 authenticated blob helper。處理 422 回應中的附件狀態與掃描錯誤，不列入 clean 附件清單。 |

### 上線前 API 契約確認

- `POST /` 的 Idempotency-Key 重試可以回傳原案件，但 API 沒有依冪等鍵查詢案件的端點。若瀏覽器重整後發生「伺服器已建立、client 未收到回應」，前端無法可靠還原原 request。上線前應決定新增冪等鍵查詢／建立結果復原能力，或制定可操作的人工查找流程；不可把新建一筆當成透明重試。
- `GET /{submissionId}` 只提供目前 revision 的明細，而審核歷程沒有舊版本欄位快照；若供應商需要逐版比較，應先補 API response 再設計該互動。
- 目前附件 422 回應可能包含 attachment metadata；共用 API error 需保留可安全解析的結構化錯誤資料，否則 UI 僅可顯示掃描未通過及重新載入／重試提示，不得將其當作附件成功。

## 7. 狀態與操作權限矩陣

| 案件狀態 | 編輯發票／明細 | 上傳附件 | 撤銷附件 | 提交／重送 | 取消 | 付款資訊 |
|---|---:|---:|---:|---:|---:|---|
| `draft` | 是 | 是 | 是 | 提交 | 是 | 不顯示 |
| `returned` | 是，新修訂 | 是，新修訂附件 | 只限未提交附件 | 重送 | 是 | 不顯示 |
| `submitted` | 否 | 否 | 否 | 否 | 否 | 不顯示 |
| `approved` | 否 | 否 | 否 | 否 | 否 | 僅顯示核准／AP 資訊，不顯示付款明細 |
| `rejected` | 否 | 否 | 否 | 否 | 否 | 不顯示 |
| `cancelled` | 否 | 否 | 否 | 否 | 否 | 不顯示 |

上表為畫面預期狀態；每次操作皆須以後端回應為準。角色限制與狀態不可操作時，前端不可用隱藏按鈕取代 API 的授權保護。

## 8. 驗收與測試

### 功能驗收

1. 供應商只能看到其登入供應商案件及伺服器提供的來源；不存在或跨供應商案件均呈現不洩露資料的找不到結果。
2. 使用者可選來源、輸入完整發票資料、建立草稿、上傳 clean 憑證並完成送審；案件編號及狀態可從清單重新開啟。
3. 缺少必填欄位、表頭與明細加總不符、精度超標或附件未 clean 時，UI 清楚指出可修正原因，伺服器仍執行最終驗證。
4. 退回案件可編輯並補件；舊的審核原因可查看。提交後資料與附件唯讀，終態案件不提供寫入操作。
5. 409 版本衝突提供重新載入並保留可恢復的表單輸入；重載取得的新版本才用於後續 `If-Match`。
6. 401／403／404／409／413／422／503 均有明確且不揭露內部資訊的提示；提交、建立或上傳期間防止重複點擊。
7. Portal 不顯示假的付款進度、預計匯款日、稅務計算或全域統計數字。

### 測試範圍

- API client 單元測試：Authorization、端點與 URL encoding、Idempotency-Key、ETag／If-Match、multipart、Blob、錯誤狀態與保留結構化 error body。
- 頁面元件測試：載入／空／錯誤狀態、狀態操作矩陣、欄位驗證、差異提示、clean 附件 gate、409 重載與取消確認。
- Playwright／瀏覽器驗證：從登入後導覽、建立草稿、附件上傳、送審、退回補件至終態檢視的主要 happy path；以受控 mock 或隔離測試 API 執行，不連正式／staging。
- 執行 `npm test`、`npm run build`，並對主要操作完成鍵盤操作、焦點可見、標籤與行動版版面檢查。

## 9. 依賴與分階段交付

1. **API client 與契約對齊**：建立型別、端點方法、ETag／If-Match、冪等與 error metadata 測試。
2. **案件清單／明細唯讀**：加入導覽、路由、狀態呈現、伺服器分頁、審核紀錄及錯誤／空狀態。
3. **建立與草稿編輯**：選擇來源、輸入發票資料、建立／更新完整草稿與版本衝突處理。
4. **附件與送審**：上傳、clean gate、撤銷／下載、提交／取消、重試及退回補件。
5. **瀏覽器驗收與啟用 Gate**：完成 OIDC 授權、附件服務、外部安全、財務／採購政策及 PostgreSQL workflow 驗收；未全部通過前不顯示可對外操作入口。

## 10. 待確認決策

- 財務確認發票號碼正規化、稅額精度、部分請款與容差政策；前端首版依 API 精確相等規則，不自行放寬。
- 供應商是否只允許 `sales` 角色寫入，或另納入 supplier admin 角色。
- 退回修改會建立新 revision，現行 API 的附件依 revision 關聯，供應商需為新 revision 重新上傳至少一份 clean 附件；若業務希望重用舊版 clean 憑證，需先擴充 API 契約與稽核規則。
- 建立請款 API 的冪等結果復原策略，以及舊修訂比較所需的 API 契約。
- 財務核准、私有物件儲存／ClamAV 部署與正式資料庫 migration 尚需另行核准；本 UI 計畫不代表可正式上線。
